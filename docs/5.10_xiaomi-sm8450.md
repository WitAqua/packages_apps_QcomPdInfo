# 5.10, xiaomi sm8450

`LineageOS/android_kernel_xiaomi_sm8450`, which is 5.10.256 and carries the
waipio parts (cupid, zeus, marble, mondrian, thor and the rest). As it ships,
the app finds nothing on it at all, and it is right to: this is a board where
none of the three ways of reading an object list exists. WitAqua's kernel now
carries the backport described further down, so the two halves of this
document are both live - the first is what the stock kernel does, the second is
what a ROM can do about it.

## Why nothing was found

**`/sys/class/usbpd`** - `drivers/usb/pd/policy_engine.c` is in the tree, but
nothing builds it: no defconfig sets `CONFIG_USB_PD_POLICY` or
`CONFIG_QPNP_USB_PDPHY`, and the waipio fragments carry only
`CONFIG_UCSI_QTI_GLINK=m`.

**`/sys/class/usb_power_delivery`** - `drivers/usb/typec/pd.c` arrived in
android14-6.1.

**`/sys/kernel/debug/usb/ucsi/*`** - `drivers/usb/typec/ucsi/debugfs.c` arrived
in android15-6.6.

Enabling qualcomm's driver does not fix it. The PD PHY it drives is a peripheral
of the charger PMIC, and `sm8450-devicetrees` has no `qcom,qpnp-pdphy` node in
`qcom/pm8350b.dtsi` - the only boards that declare one are the pm7250b ones
(holi, parrot, diwali, ravelin). On sm8450 the policy engine runs in the charger
firmware and the AP sees it over pmic-glink, through UCSI, or not at all.

## What the kernel does have

The objects are read. This 5.10 predates the `UCSI_CAP_PDO_DETAILS` gate on
`ucsi_get_pdos()` - that is android16-6.12 - so `ucsi_pwr_opmode_change()` keeps
both halves whenever a contract is in force:

```c
con->rdo = con->status.request_data_obj;
typec_set_pwr_opmode(con->port, TYPEC_PWR_MODE_PD);
ucsi_get_src_pdos(con, 1);
```

`con->src_pdos[]`, `con->num_pdos` and `con->rdo` all sit in
`struct ucsi_connector`. Nothing publishes them. The only thing that leaks out
is what `psy.c` derives, in `/sys/class/power_supply/ucsi-source-psy-<dev>0`:

```
online usb_type voltage_min voltage_max voltage_now current_max current_now
```

`voltage_now` is `pdo_fixed_voltage(src_pdos[rdo_index(rdo) - 1])` and
`current_now` is `rdo_op_current(rdo)`. Both read the fixed-supply fields of
whatever word they are given, so on a PPS contract they land on the wrong bits,
and `ucsi_psy_get_usb_type()` only ever answers `PD`, never `PD_PPS`.

Which kind of contract it is comes from the charger instead -
`/sys/class/qcom-battery/usb_real_type`, out of `qti_battery_charger`, which is
the charger on this board as on every other pmic-glink one. See
[kernel.md](kernel.md); it is what decides whether the two figures above are
shown at all.

## What the app does about it

On the stock kernel, `UcsiSupplySource` reads the type-C class and that supply:
the port, the roles, whether a contract was negotiated, the charger's name for
the adapter, and UCSI's own voltage and current - held back where the adapter is
`PD_PPS`, because there they would be nonsense, and shown with the reason where
it is not. No object list, because there is none to read, and that too is said
rather than left as an empty page.

## The backport

Of the three ways of fixing this - debugfs, an invented `usbpd`-shaped class, or
the upstream class - WitAqua's kernel took the third and added the one thing it
does not have. The other two were left: debugfs needs root and a mount, which a
ROM should not count on, and an invented ABI is a worse thing to carry than an
upstream one.

**`usb_power_delivery`, out of android14-6.1.** `drivers/usb/typec/pd.c` and
`pd.h` verbatim, the `pd` pointers on `typec_partner` and `typec_port` with the
three functions that set them, and `usb_power_delivery_init()` in the class's
own module init. The UCSI side registers the partner's objects when a contract
comes up and the port's own at registration, which meant splitting
`ucsi_get_pdos()` into a read and a loop the way upstream did, since the
partner's list can run past the four objects one UCSI command returns.

Two things that are not upstream and are worth knowing about:

- **`typec_port_to_dev()`**. `struct typec_port` is private to `class.c`, and
  creating an attribute on a port from the UCSI driver needs its `struct
  device`. A one-line accessor beside the others.
- **`/sys/class/typec/portN/rdo`**, the request object as one hex word, shown
  from `con->rdo` and `sysfs_notify()`d when a contract changes. The class has
  no request at any kernel version; without this the board shows the whole menu
  and not the line that was ordered from it. See
  [kernel.md](kernel.md#where-this-should-end-up).

### What it looks like on the handset

Measured on diting (Xiaomi 12T Pro) with a 100W charger, 2026-09-16:

```
/sys/class/usb_power_delivery/pd0                      the port's own
/sys/class/usb_power_delivery/pd1/source-capabilities  5V 9V 12V 15V 20V, 3A each
/sys/class/typec/port0/rdo                             0x230320c8
```

`pd0` is registered and holds no capabilities. That is the firmware rather than
the backport: `GET_PDOS` with the partner bit clear returns nothing on this
board, so the port has no local PDOs to register and the app shows no sink
capabilities. The partner's list is complete, which is the one that matters.

`0x230320c8` decodes to object 2 at 2A - 9V, the second line of that menu.

### Building it

`CONFIG_TYPEC` and `CONFIG_TYPEC_UCSI` are both `y`, so the class and the
attribute are inside `boot.img`. `CONFIG_UCSI_QTI_GLINK` is `m`, and
`ucsi_glink.c` indexes `udev->ucsi->connector[]` - the struct this adds fields
to - so **`vendor_dlkm` has to be flashed with the same kernel**. A `boot.img`
on its own leaves the module computing the wrong offsets.

## For the ROM build

`system_app` reads none of this on a stock policy. On the backported kernel it
is the power delivery class and the type-C class that matter:

```
allow system_app sysfs_usb_pd:dir r_dir_perms;
allow system_app sysfs_usb_pd:file r_file_perms;
allow system_app vendor_sysfs_usb_c:dir r_dir_perms;
allow system_app vendor_sysfs_usb_c:file r_file_perms;
allow system_app vendor_sysfs_usb_supply:file r_file_perms;
```

Those two types are what diting labels them; check the handset rather than
trusting the list, since neither the UCSI supply nor the class is always the
same type as the charger's. Without the backport, drop the first pair - there is
no class to read - and keep the rest.
