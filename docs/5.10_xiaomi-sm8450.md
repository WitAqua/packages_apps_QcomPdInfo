# 5.10, xiaomi sm8450

`LineageOS/android_kernel_xiaomi_sm8450`, which is 5.10.256 and carries the
waipio parts (cupid, zeus, marble, mondrian, thor and the rest). The app found
nothing on it at all, and it was right to: this is a board where none of the
three ways of reading an object list exists.

## Why nothing was found

**`/sys/class/usbpd`** - `drivers/usb/pd/policy_engine.c` is in the tree, but
nothing builds it: no defconfig sets `CONFIG_USB_PD_POLICY` or
`CONFIG_QPNP_USB_PDPHY`, and the waipio fragments carry only
`CONFIG_UCSI_QTI_GLINK=m`.

**`/sys/class/usb_power_delivery`** - `drivers/usb/typec/pd.c` arrived in
android14-6.1.

**`/sys/kernel/debug/usb/ucsi/*`** - `drivers/usb/typec/ucsi/debugfs.c` arrived
in android15-6.6.

Enabling qualcomm's driver does not fix it. The PD PHY it drives is a peripheral
of the charger PMIC, and `sm8450-devicetrees` has no `qcom,qpnp-pdphy` node in
`qcom/pm8350b.dtsi` - the only boards that declare one are the pm7250b ones
(holi, parrot, diwali, ravelin). On sm8450 the policy engine runs in the charger
firmware and the AP sees it over pmic-glink, through UCSI, or not at all.

## What the kernel does have

The objects are read. This 5.10 predates the `UCSI_CAP_PDO_DETAILS` gate on
`ucsi_get_pdos()` - that is android16-6.12 - so `ucsi_pwr_opmode_change()` keeps
both halves whenever a contract is in force:

```c
con->rdo = con->status.request_data_obj;
typec_set_pwr_opmode(con->port, TYPEC_PWR_MODE_PD);
ucsi_get_src_pdos(con, 1);
```

`con->src_pdos[]`, `con->num_pdos` and `con->rdo` all sit in
`struct ucsi_connector`. Nothing publishes them. The only thing that leaks out
is what `psy.c` derives, in `/sys/class/power_supply/ucsi-source-psy-<dev>0`:

```
online usb_type voltage_min voltage_max voltage_now current_max current_now
```

`voltage_now` is `pdo_fixed_voltage(src_pdos[rdo_index(rdo) - 1])` and
`current_now` is `rdo_op_current(rdo)`. Both read the fixed-supply fields of
whatever word they are given, so on a PPS contract they land on the wrong bits,
and `ucsi_psy_get_usb_type()` only ever answers `PD`, never `PD_PPS`.

Which kind of contract it is comes from the charger instead -
`/sys/class/qcom-battery/usb_real_type`, out of `qti_battery_charger`, which is
the charger on this board as on every other pmic-glink one. See
[kernel.md](kernel.md); it is what decides whether the two figures above are
shown at all.

## What the app does about it

`UcsiSupplySource` reads the type-C class and that supply: the port, the roles,
whether a contract was negotiated, the charger's name for the adapter, and
UCSI's own voltage and current - held back where the adapter is `PD_PPS`,
because there they would be nonsense, and shown with the reason where it is not.
No object list, because there is none to read, and that too is said rather than
left as an empty page.

## Getting the whole thing

In order of how much kernel there is to touch. The first is the one worth doing.

**Backport `ucsi/debugfs.c` from android15-6.6.** Roughly 130 lines and one
`struct dentry *` on `struct ucsi`, plus its `Kconfig` entry and `debugfs.o` in
the Makefile. `ucsi_send_command()` is already `EXPORT_SYMBOL_GPL` here, which
is all the file needs. With it mounted the app's own debugfs reader gets both
the object list (`GET_PDOS`) and the request (`GET_CONNECTOR_STATUS`), so the
sideloaded build becomes complete - it needs root and debugfs mounted, which is
what [Qcom-PD-Info-Module](https://github.com/WitAqua-tools/Qcom-PD-Info-Module)
is for, so a ROM should not count on it.

**Publish `src_pdos[]` and `rdo`.** An attribute group on `ucsi->dev` printing
them as hex words is a few dozen lines and needs no root at all. Shaped like
qualcomm's driver - `pdo1`..`pdo7`, `rdo`, `contract`, `current_pr`,
`current_dr`, under a class named `usbpd` - the app reads it with no change,
because that is `QualcommSource`. It is an invented ABI either way, so it suits
a ROM kernel rather than anything headed upstream; for upstream, see the two
changes in [kernel.md](kernel.md).

**Backport the class.** `pd.c` and the UCSI registration beside it, out of
android14-6.1. Most work of the three, and it still has no request object, so
one of the two above is wanted anyway.

## For the ROM build

`system_app` reads none of this on a stock policy. What matters here is the
type-C class and the UCSI supply rather than a PD PHY subtree:

```
allow system_app vendor_sysfs_usb_c:dir r_dir_perms;
allow system_app vendor_sysfs_usb_c:file r_file_perms;
allow system_app vendor_sysfs_usb_supply:file r_file_perms;
```

Check the labels on the handset rather than trusting that list - the UCSI supply
is not always the same type as the charger's.
